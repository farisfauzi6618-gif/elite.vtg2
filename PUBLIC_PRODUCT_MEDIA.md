# Public product media

The existing `/api/product-images/:key?size=...` URL remains the public entry point. Publication is checked before a 60-second-cacheable 307 redirects to a ready WebP in a separate public Blob store. This removes the image response body from the Function on the direct path. Function invocations still occur on redirect-cache misses, and Blob/CDN delivery is still metered.

`PRODUCT_MEDIA_READ_WRITE_TOKEN` must belong to the dedicated public store. It is server-only, Production-only, and never substitutes for the private store's `BLOB_READ_WRITE_TOKEN`. Preview deployments and `PRODUCT_MEDIA_DISABLED=1` retain the old renderer. Originals, drafts, inactive color photos, payment evidence and QRIS stay in their existing private store.

Migration `release_0019_public_product_media.sql` adds only cache metadata. A cross-instance lease permits one builder per photo/preset/pipeline. Ready requests do not take a write transaction. Paths include a generation UUID, so an expired builder cannot overwrite a new generation. The image route has a 60-second maximum duration; leases last 120 seconds. Only WebP produced by the existing renderer is eligible; original/decoder fallback bytes are never copied into the public store. Preset, framing and quality are unchanged. Metadata is stripped during WebP encoding.

No batch backfill: derivatives are built on demand. A file must be at most 512 KiB. The application ledger reserves the maximum file size for builders/revocations and caps accounted derivatives at 128 MiB across all pipelines. Metadata, provider accounting/cache overhead, and any manually uploaded unrelated files are outside that application cap. Cap exhaustion falls back to the original preview route without blocking browsing. Do not manually add files to this store.

Saving a product withdraws no-longer-public keys; trash does the same. Shared published references are retained. Publication and generation ownership are rechecked after upload. Failed deletions remain `revoked`, keep their budget reservation, and are retried in a bounded batch after authenticated admin mutations using Next `after`; no new cron/polling/log stream is installed. In-flight builders keep their ledger entry until completion or lease expiry. A failed provider deletion can delay removal until a retry succeeds. Public Blob deletion/cache propagation may take up to 60 seconds, and previously downloaded browser/crawler copies cannot be recalled.

Malformed URLs, unavailable storage/database, an unconfigured store, unsupported images and full cache all keep the existing preview fallback. Existing client image-error fallback remains available. Direct links, galleries, selected-color images, share and zoom use their existing routes and UI. Checkout/auth/stock/payment modules are not modified.

Rollback: set `PRODUCT_MEDIA_DISABLED=1` and redeploy. Metadata/original records are not deleted by rollback. To rotate a store, first disable delivery, withdraw ready assets from the old store, and reconcile the ledger before replacing credentials; do not silently repoint this token while old ready rows exist.

Verification: `node --expose-gc --test --test-concurrency=1 tests/*.test.mjs`, typecheck and production build. Explicit GC activates the existing local-libSQL fixture cleanup hook on Windows; production uses remote libSQL. The monolith test keeps the Next server package external, like the deployment runtime. Tests cover privacy, metadata stripping, byte limits, generation races, shared references, unpublish/trash, retry, failure fallback and existing commerce regressions.

Sources: [Public Blob](https://vercel.com/docs/vercel-blob/public-storage), [Private Blob](https://vercel.com/docs/vercel-blob/private-storage), [CDN cache headers](https://vercel.com/docs/caching/cache-control-headers). Measure normalized FOT, Blob transfer/operations, Function CPU and cache metrics after rollout; no fixed dollar savings are promised.
